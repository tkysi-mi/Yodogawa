# VerifyIssueFacts

## 目的

- GitHub Issue の記述（主張・前提・参照ファイル）をコードベースの現状と照合し、各主張を【事実 / 誤り / 不明】に判定する。
- 各判定に `file_path:line` の証拠を必ず添える。
- Issue が触れていない関連箇所（呼び出し元・依存・連動箇所）を網羅し、影響範囲マップを提示する。
- Issue 対応に着手する前の「事実確認」を一度で済ませる。

## 制約（最重要）

<critical>
- このスキルは**読み取り専用**。`allowed-tools` に `Write`/`Edit`/`NotebookEdit` を含めず、Bash も読み取り専用コマンド（`gh issue/pr view`, `git log/blame/show/diff/grep`）にスコープしている。**コードもファイルも一切編集・作成しない。**
- 検証結果は**チャットに出力するのみ**。レポートをファイル保存しない。
- 「修正すべき」と判断しても、修正の実装・提案コードの記述はこのスキルの責務外。**事実の提示にとどめる**。
- 確証が持てない主張は無理に【事実】【誤り】に倒さず【不明】とし、何を確認すれば確定するかを書く（confident なバイアスを避ける）。
</critical>

## 手順

`$ARGUMENTS` に issue 番号または URL があればそれを対象にする。なければ手順1で確認する。

### 1. Issue の取得

```bash
gh issue view <番号> --comments
# ↑ が空を返す環境では JSON で確実に取得する:
gh issue view <番号> --json number,title,state,body,author,labels,comments
```

- 本文に加えコメントも取得し、議論で更新された前提も拾う（**後のコメントが本文を上書きする**ことがある＝最新の合意を採る）。
- `$ARGUMENTS` 未指定なら、対象の issue 番号をユーザーに確認する。`gh` が使えない／本文が手元にしかない場合は本文の貼り付けを促す。
- リポジトリは通常 origin 既定で解決されるので `--repo` は不要。曖昧なときだけ `--repo tkysi-mi/Yodogawa` を付ける。
- Issue が PR を参照していれば `gh pr view <番号>` で関連差分の文脈を補う。

### 2. 主張の分解

Issue 本文・コメントを読み、**検証可能な命題（claim）** に分解して箇条書きにする。後で1つずつ判定する。

例:

- 「スキル X の SKILL.md が frontmatter に name/description を持つ」
- 「CLI（bin/cli.js）が templates/ を対象の `.claude/` 配下にコピーする」
- 「テンプレ Y の内部リンク `[z](reference/...)` が壊れている」
- 「package.json の files に skills が含まれる」

主観・要望（「〜したい」「〜すべき」）はコードと照合できないので claim から除外し、別途「要望」として控える。**Issue の修正案・受け入れ基準も claim ではないが破棄せず別掲し、#2（検証方法）・#3（実装計画）への引き継ぎとして残す。**

### 3. 各 claim のコード照合

claim ごとに該当コードを特定して実挙動を読み取る:

- 参照ファイル／シンボルは **Read** で開く。
- シンボル・文字列は **Grep**、ファイル探索は **Glob**。
- 経緯・いつ変わったかの確認が要るときのみ `git log -p <path>` / `git blame <path>` / `git show <sha>`。

判定を付ける:

| 判定 | 意味 |
|------|------|
| 事実 | コードが主張通りに書かれている／振る舞う |
| 誤り | コードは主張と異なる（実際の挙動を併記する） |
| 不明 | コードだけでは確定できない（動的確認・実行が必要、外部依存など） |

**各判定に必ず `file_path:line` ＋ 該当行の短い引用を証拠に添える。** 証拠のない判定は出さない（引用は行 drift に強い）。

**判定の指針（特に間違えやすい点 — ばらつきを防ぐため必ず適用）:**

- **行番号を鵜呑みにしない**: 引用された行はコード変更で drift しうる。シンボル/文字列で Grep し直し、**主張の実体**で判定する。実体が正しく行番号だけズレているなら【事実】とし、証拠に「実際は path:実行番号（cited は X）」と注記する。**行ズレだけを理由に【誤り】にしない。**
- **「字面」と「実行時の帰結」を分ける**: 「コードがこう書いてある」と「実行時にこう振る舞う/帰結する」は別物。主張がどちらを指すか見極め、食い違うなら両方を併記する（例: 字面は【事実】だが別のゲートで帰結が変わるので操作的主張は【誤り】、のように分解）。framing・解釈・因果（「〜なので遅い/無意味」）の主張は検証可能な命題に割って個別判定する。
- **数量主張は実数で**: 「N箇所 / N ファイル / N スキル」は、数え方（母集団。例: `skills/` 配下の SKILL.md、`**/*.md` 全体など）を**明示**し、**自分で数えた実数**と突き合わせて判定する。母集団が曖昧なら不明点に挙げる。

### 4. 関連箇所の網羅マップ

claim に登場したシンボル・パス・スキル名／ディレクトリ名・設定キー・定数について:

- **呼び出し元・参照箇所**を Grep で洗い出す（例: `bin/cli.js` のコピー対象、`package.json` の `files`、SKILL.md 間の相互参照）。
- 同じパス／キー／定数を使う**連動箇所**を探す。
- 「Issue は触れていないが、この変更で影響しうる箇所」を列挙する（影響範囲の取りこぼし防止）。

### 5. レポート出力（チャットのみ）

下記フォーマットでチャットに出力する。ファイルには書かない。

## 出力フォーマット

```
## Issue #<n> 事実確認レポート

### サマリ
<1-2文。主張は概ね正しい / 一部誤り / 不明点あり 等>

### 主張ごとの判定
| # | 主張 | 判定 | 証拠 | 備考 |
|---|------|------|------|------|
| 1 | ... | 事実 | path:line | ... |
| 2 | ... | 誤り | path:line | 実際は〜 |

### 関連箇所マップ（影響範囲）
- <symbol/key>: 参照元 path:line, path:line ...
- Issue 未言及だが関連: path:line — 理由

### 不明点 / 動的確認が必要な項目（→ #2 検証レディネスへ）
- <静的に確定できず動的確認が要る claim。何を確認すれば確定するか>

### 引き継ぎメモ（→ #3 計画へ）
- <Issue の修正案・受け入れ基準など、claim ではないが対応時に必要な前提>
```

## 完了条件

- すべての claim に判定と `file_path:line` ＋ 引用の証拠がついている。
- 判定の指針が適用されている（行ズレは注記し誤判定しない／字面と実行時帰結を分離／数量は実数で判定）。
- 関連箇所マップが提示されている。
- 動的確認が要る claim（→ #2）と Issue の修正案・受け入れ基準（→ #3）が引き継ぎとして残されている。
- **ファイル・コードの変更が一切ない**（読み取り専用を遵守）。
