# ユーザーストーリー作成ガイド

`05-user-stories.md` を書くときの原則・フォーマット・ベストプラクティス集。テンプレートは記入欄中心に保ち、
詳しい考え方が必要なときに本ガイドを参照する。

## ユーザーストーリーとは

ユーザー視点の機能要求を物語形式で記述したバックログ。詳細仕様ではなく**議論の出発点（会話のきっかけ）**として機能する。

- **目的**: ユーザーの課題とニーズの明確化 / 開発チームとステークホルダーの共通理解 / 開発優先度の判断材料 / スプリント計画の基礎資料。
- **特徴**: 実装方法ではなくユーザーの「なぜ」に焦点。継続的に追加・更新・削除される Living Document。

## INVEST 原則

良いストーリーの 6 条件。

- **Independent（独立）**: 他ストーリーへの依存が少ない
- **Negotiable（交渉可能）**: 詳細は会話で詰められる余地がある
- **Valuable（価値）**: ユーザー/ビジネスに価値がある
- **Estimable（見積可能）**: 規模を見積もれる
- **Small（小さい）**: 1〜2 週間のスプリントで完了できるサイズ
- **Testable（テスト可能）**: 完了を検証できる

記載粒度: 大きすぎる場合は Epic として分割、小さすぎる場合は他ストーリーと統合を検討する。

## ストーリーのフォーマット

標準: 「**[役割]として、[目的]がしたい、なぜなら[理由]**」（英: "As a [role], I want [goal] so that [benefit]"）。

- **役割（Who）**: ユーザーの種類やペルソナ（例: 新入社員 / 管理者 / エンドユーザー）。`01-product-brief.md` のペルソナ表の ID（P-XXX）を「ペルソナ」列で参照し、役割名をその記載と一致させる（役割を宙に浮かせない）。該当ペルソナが無ければ Product Brief 側に追加する。
- **目的（What）**: 実現したい機能や行動（例: プロフィールを編集したい）
- **理由（Why）**: その機能が必要な理由・得られる価値（例: 自分の情報を最新に保つため）

書き方のコツ: 技術用語を避けユーザーの言葉で書く / 実装方法（How）ではなく目的（What・Why）に集中 / 1 ストーリー 1 価値 / 曖昧さを避け具体的に。

## 受け入れ基準（Acceptance Criteria）

ストーリーが「完了」と判断できる明確な基準。測定可能・テスト可能・Yes/No で判定可能であること。

**フォーマット1: Given-When-Then（BDD 形式）**

```
Given [前提条件]
When  [アクション]
Then  [期待される結果]
```

例: `Given ログイン済みユーザーが自分のプロフィールページにいる時 / When 「編集」して保存すると / Then 変更後の名前が表示される`

**フォーマット2: チェックリスト形式**

- [ ] ユーザーは名前・メール・画像を編集できる
- [ ] 保存時にバリデーションエラーが表示される

書き方のベストプラクティス: 最低 1 個、通常 3〜7 個 / UI の細かい仕様ではなくビジネス価値の検証に焦点 / 「意図」を書き「実装方法」は書かない / 開発者とテスターが明確にテストできる内容にする。

## 優先度

開発順序の判断材料。一般的な分類:

- **High**: 必須機能、ビジネス価値が高い、依存が多い
- **Medium**: 重要だが緊急ではない、代替手段がある
- **Low**: あると良い、将来検討

考慮要素: ビジネス価値 / 緊急性 / リスク / 工数（ROI）/ 依存関係。

注意: 優先度は変動する（定期見直し）。すべてが High になる状況を避け、真の優先順位をつける。最終決定権はプロダクトオーナー。

> MVP の取捨選択（Must / Not Now / Won't）と検証仮説への紐づけは `/a-002a-slice-mvp-scope`（`02-mvp-scope.md`）が担う。
> 本ガイドの「優先度」は実装順の目安であり、MVP スコープ判断とは役割を分ける。

## 全体のベストプラクティス

- **3C 原則**: Card（カード）/ Conversation（会話）/ Confirmation（確認）。
- ストーリーはチーム全員（PO・開発・デザイナー・QA）で作成する。
- 定期的なリファインメントで詳細化・分割・統合する。
- 完了の定義（DoD）を明確にする。実装後のフィードバックを次のストーリーに反映する。
- テクニカルストーリー（リファクタリング・技術的負債解消）も含めてよい。
