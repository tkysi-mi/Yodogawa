# ユビキタス言語 整備ガイド

`02-ubiquitous-language.md` を書くときの原則・記載のポイント・運用方法。テンプレートは用語表を中心に保ち、
詳しい考え方が必要なときに本ガイドを参照する。Event Storming 全体の観点は
[event-storming-guide.md](event-storming-guide.md) を参照。

## ユビキタス言語とは

プロジェクト全体で共有される共通言語の定義集。Domain-Driven Design の中核概念で、ビジネス用語と技術用語の橋渡しをする。

- **目的**: 開発者とドメインエキスパートの共通理解構築 / 用語の曖昧さ排除 / コード・ドキュメント・会話で一貫した用語使用 / 新メンバーのオンボーディング支援。
- すべてのコミュニケーション（コード・会話・ドキュメント）で同じ言葉を使う。
- **Bounded Context ごとに定義される**（同じ用語でも Context が異なれば意味が異なる場合がある）。`[Bounded Context 共通]` セクションを設けて全体共通の用語を記すのも有効。

## 用語の記載ポイント

| 列 | 書き方 |
|---|---|
| 用語 | ドメインエキスパートが使う正式な用語。単複を明確に（Order / Orders）。日本語は表記ゆれ注意（「ユーザ」か「ユーザー」か統一）。略語は避けフルスペル。 |
| 定義 | 1〜3 文で明確に。その Context 内での意味を正確に。実装詳細ではなくビジネス的意味を、エキスパートと合意した形で書く。 |
| 使用例 | コード例（クラス名・メソッド名・変数名）/ ドキュメント例 / 会話例。複数あれば箇条書き。 |

- ドメインエキスパートが使う言葉を優先し、技術用語ではなくビジネス用語で記述する。
- クラス名・メソッド名・変数名にも反映する。
- 動詞（Order = 注文する, Ship = 出荷する）や状態遷移に関わる語（Pending, Confirmed, Shipped）も含める。
- 類似用語の違いを明確にする（例: Customer vs User）。

## 禁止用語

使用を避けるべき曖昧・誤解を招く用語を記録する。目的は用語の混乱防止、新メンバーへの注意喚起、コードレビューのチェックリスト。

記載すべき用語: 複数の意味を持つ曖昧な語 / 技術用語とビジネス用語が混在する語 / 過去に混乱を招いた語 / Context により意味が変わる語 / 意味が不明瞭な略語。

各エントリには **なぜ禁止か** と **代替となる明確な用語** を必ず添える。

## Living Document として運用する

ドメイン理解が深まるにつれ継続的に更新する。

- ドメインモデリング時に初版作成。Event Storming やレビュー時に追加・修正。混乱や不一致が見つかったら即更新。
- Git で変更履歴を追跡し、チーム全員がアクセスできる場所（Wiki / Confluence 等）に置く。
- 用語変更はコード全体への影響が大きいため慎重に。変更時はリファクタリングタスクを作成する。
- 用語の進化を歓迎する（ドメイン理解が深まった証）。図やダイアグラムを併用すると理解が深まる。

## コード・コミュニケーションとの整合

- コードレビュー時に本ドキュメントを参照する。可能なら CI/CD で用語の lint チェックを自動化する。
- ドメインエキスパートとの会話・仕様書でも必ずこの用語を使う。
- 命名規則（クラス/メソッド/変数）・表記規則（単複・大文字小文字）・言語選択（英/日）のルールを「メモ」に明記する。
