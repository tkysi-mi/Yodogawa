# 一貫性チェックの詳細項目

SKILL.md 手順4「一貫性チェック」で参照する詳細項目。**6観点すべて doctor 非対応**（`structure`/`id-trace`/`placeholder` は `docs/project` 固定で `docs/tasks/` を検査対象にしない。唯一 `links` が `docs/` 全体を検査するが、相対リンク切れの検出に限られ意味的整合性は見ない）。すべて `a-definition.md` / `b-research.md` / `c-implementation.md` を Read して判断し、判定には file:line の引用を必須とする。番号は SKILL.md 手順4の観点表（1〜6）に対応する。

## チェック1: タスク定義 ↔ 実装計画（変更内容のカバレッジ）

### 1.1. 変更内容と実装ステップのマッピング

- タスク定義（a-definition.md）の「変更内容一覧」を抽出：
  - 画面（追加・変更する画面やコンポーネント）
  - データモデル（テーブル、カラムの追加・変更）
  - API（エンドポイントの追加・変更）
  - その他（環境設定、インフラ、ツール）

- 実装計画（c-implementation.md）の各ステップと成果物を抽出

- 各変更内容に対応する実装ステップが存在するか確認

**チェック項目**:

- [ ] すべての画面変更に対応する実装ステップが存在する
- [ ] すべてのデータモデル変更に対応する実装ステップが存在する
- [ ] すべてのAPI変更に対応する実装ステップが存在する
- [ ] その他の変更（環境設定など）に対応する実装ステップが存在する

**検出すべき問題**:

- ❌ **Error**: タスク定義で言及された変更に対応する実装ステップがない
- ⚠️ **Warning**: 実装計画で定義されているステップがタスク定義の変更内容に含まれていない（スコープ外の作業の可能性）

### 1.2. 成果物の具体性チェック

- 実装計画の各ステップの成果物を確認
- 成果物が具体的なファイル名・コンポーネント名で記載されているか確認

**検出すべき問題**:

- ⚠️ **Warning**: 成果物が抽象的すぎる（例: 「フォームの実装」→ 具体的なファイル名が必要）
- ⚠️ **Warning**: 成果物が記載されていないステップがある

## チェック2: タスク定義 ↔ 実装計画（ユーザーストーリーのカバレッジ）

### 2.1. ユーザーストーリーと実装ステップの対応

- タスク定義（a-definition.md）のユーザーストーリー一覧を抽出
- 各ユーザーストーリーについて、実現するための実装ステップが存在するか確認

**チェック項目**:

- [ ] すべてのユーザーストーリーに対応する実装ステップが存在する
- [ ] ユーザーストーリーの「何をしたい（目的）」が実装で実現されている

**検出すべき問題**:

- ❌ **Error**: ユーザーストーリーに対応する実装ステップがない

## チェック3: タスク定義 ↔ 実装計画（受け入れ基準のカバレッジ）

### 3.1. 受け入れ基準と実装ステップの対応

- タスク定義（a-definition.md）の受け入れ基準一覧を抽出
- 各受け入れ基準を満たす実装ステップ（またはテスト計画）が c-implementation.md に存在するか確認

**チェック項目**:

- [ ] すべての受け入れ基準に対応する実装ステップ・テストが存在する
- [ ] 受け入れ基準が「誰が読んでも同じ判定になる」具体性を持つ（例: 「正しく動作する」のような検証不能な表現でない）

**検出すべき問題**:

- ❌ **Error**: 受け入れ基準に対応する実装ステップ・テストが c-implementation.md に無い
- ⚠️ **Warning**: 受け入れ基準の表現が曖昧で検証方法が定まらない

## チェック4: リサーチ ↔ 実装計画

### 4.1. 技術選定・リスク対策の反映

- リサーチ（b-research.md）の技術選定が実装計画（c-implementation.md）のステップに反映されているか確認
- リサーチで挙げたリスクへの対策が実装計画に含まれているか確認

**チェック項目**:

- [ ] 選定技術が実装計画のステップと矛盾しない
- [ ] リサーチで指摘したリスクごとに、対応する対策・ステップが実装計画にある

**検出すべき問題**:

- ❌ **Error**: b-research.md の技術選定と c-implementation.md の記述が矛盾する
- ⚠️ **Warning**: リサーチで挙げたリスクへの対策が実装計画に見当たらない

## チェック5: 実装計画の完全性

### 5.1. フェーズ・ステップ・テスト計画の妥当性

- フェーズ分割: 各フェーズに目的・完了条件が明記され、後続フェーズが依存する成果物が先行フェーズで作られているか確認
- ステップ粒度: 1ステップが数時間規模に収まる具体性か（オープンエンドな粗いステップが無いか）確認
- テスト計画: 各受け入れ基準に対応するテスト（ユニット/統合/E2E）が計画されているか確認

**チェック項目**:

- [ ] 各フェーズに完了条件が明記されている
- [ ] 後続フェーズが依存する成果物が先行フェーズのステップに含まれる
- [ ] ステップ粒度が実装可能な単位に分割されている
- [ ] 受け入れ基準を網羅するテスト計画がある

**検出すべき問題**:

- ❌ **Error**: フェーズの完了条件が無い、または後続フェーズが依存する成果物がどのフェーズにも存在しない
- ⚠️ **Warning**: ステップ粒度が大きすぎる（分割検討）、テスト計画が受け入れ基準の一部を欠く

## チェック6: タスク全体の実現可能性

### 6.1. 目的・スコープ・依存関係の整合性

- 目的との整合性: a-definition.md の目的と c-implementation.md の成果物が一致するか確認
- スコープの適切性: 変更内容がタスクとして妥当な粒度か（分割すべき規模でないか）確認
- 依存関係の明示: 他タスク・外部チーム・環境変数等への依存が明記されているか確認

**チェック項目**:

- [ ] a-definition.md の目的と実装計画の成果物が一致する
- [ ] スコープが単一タスクとして妥当な粒度である
- [ ] 他タスク・外部要因への依存が明記されている

**検出すべき問題**:

- ❌ **Error**: 目的と実装計画が矛盾する、または必須の依存関係が未記載
- ⚠️ **Warning**: スコープが広すぎる（タスク分割を検討）
